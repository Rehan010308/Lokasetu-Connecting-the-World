## 2. The one place I did not follow the spec

You asked for `phone text` on `profiles`. It is not there.

`profiles` has to be world-readable — it is the directory of who does what work,
and the feed, search and every public profile page read it. **Row Level Security
is per row, not per column.** A phone column on that table is readable by anyone
holding the anon key, whatever the UI chooses to render. Your rule *"public
feeds never expose phone numbers"* would have been a convention rather than a
fact, and a two-line `curl` would break it.

So the phone number and the exact address live in a new `private_details` table
whose policy enforces the rule you actually asked for:

```sql
using (
  auth.uid() = owner_id
  or exists (select 1 from public.offers o
              where o.status = 'accepted'
                and ((o.employer_id = owner_id and o.worker_id = auth.uid())
                  or (o.worker_id = owner_id and o.employer_id = auth.uid()))
                and (private_details.post_id is null or o.post_id = private_details.post_id))
)
```

Locality — city, area, society — did go on `profiles`, because that is the
"area only" you want visible before acceptance.

## 5. What each feature does now

**Multilingual (1).** Already shipped in v5.0.0 — ten languages, every page,
compile-enforced. New in v4.3: the choice is saved to
`profiles.preferred_language`, so it follows the account onto a new device.
localStorage still holds it for signed-out visitors.

**Google Maps (2).** After acceptance the worker gets **Open in Google Maps**,
built from `https://www.google.com/maps/search/?api=1&query=<address>`. No
embed, no SDK, no key.

**Contact (3).** After acceptance: the worker sees the customer's name, phone
and street address; the customer sees the worker's name and phone. Before
acceptance both sides see the area and a line saying when it unlocks.

**Permissions (4).** Enforced three times: the composer offers only the post
type matching the account, the `posts_guard_role` trigger raises on anything
else, and offers were already employer-only by RLS. The role itself has been
immutable since v5.0.0 via `freeze_profile_role`.

**Address flow (5).** City, area and society asked once at sign-up. The job
composer never asks again — it shows the locality read back from the profile and
asks only flat number, landmark and notes, which go to `private_details`.

**Realtime (7).** Already on for posts, offers and connections;
`private_details` added, so a revealed phone appears without a refresh.

## 6. Rollback

**Code — instant:**

```powershell
git checkout backup/pre-v4.3-multilingual
```

**Database — the migration is additive, so nothing needs undoing.** If you want
it gone anyway:

```sql
drop trigger if exists posts_guard_role on public.posts;
drop function if exists public.guard_post_role();
drop table if exists public.private_details cascade;
alter table public.profiles
  drop column if exists city,
  drop column if exists area,
  drop column if exists society,
  drop column if exists preferred_language;
```

Dropping the trigger alone is enough to undo Feature 4 without touching data.
